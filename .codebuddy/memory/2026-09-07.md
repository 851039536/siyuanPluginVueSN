## gitPush 历史重写性能优化：commit-tree 逐条重建 → fast-import 单进程流式重建

用户反馈改/删一个很早的历史提交时（1000+ 条后续提交都要重算 hash）耗时巨量。经问答确认采用 GitHub filter-repo 同款底层机制（fast-import 单进程流式重建），边界约束：保持现有语义（不碰工作区/暂存区、不拍平 merge 侧链、失败不影响仓库）+ 改动收敛在重写层（managers/）。改动 5 个文件：

1. **GitExecutor.ts**：新增 `execGitStreaming(cwd, args, input, opts)` —— 基于 spawn 的 stdin 流式长驻进程执行（返回 stdout **Buffer**，tree 内容二进制需无损），复用本地并发池/activeProcesses 生命周期/2000 字节 stderr 摘要错误；持续消费 stdout/stderr 防管道死锁。
2. **historyRewritePlan.ts**（新）：RewriteEntry/RewritePlan 共享类型（HistoryRewriter 预计算 → FastImportRewriter 执行，独立文件避免循环依赖）。
3. **FastImportRewriter.ts**（新）：`cat-file --batch` 单进程批量查 tree 顶层条目（二进制解析 + tree hash 去重缓存）→ 构造 fast-import 流（每条 commit：`deleteall` + 全量 `M` 指令的完整 tree 模型，同条目集合同 tree hash，内容不变语义）→ `fast-import --force --quiet --done` 导入临时 ref `refs/gprw/<branch>` → finally 删临时 ref → rev-parse 取 newTip 供 CAS。细节：tree 条目名保持原始字节（Buffer 拼接，无损非 UTF-8 文件名）；含特殊字节的路径走 C 风格引号转义（quoteFastImportPathBytes）；git 内部目录 mode "40000" 归一化 fast-import 的 "040000"；raw 时间 `<epoch> <±HHMM>`（FMT 补 %at/%ct，ISO 时区尾去冒号）；preserveDate=false 时 committer 显式当前时间+本地时区（对齐旧方案不设 GIT_COMMITTER_DATE 的语义）；进度每 100 条 setTimeout(0) yield 让 Vue 渲染。
4. **HistoryRewriter.ts**：重写 rebuildDag —— parseLog 补 at/ct 字段；onTarget 策略注入改为 TargetAction 联合类型（rewrite/drop）；buildPlan 预计算重建计划（拓扑序、侧链 identity 跳过、drop 别名链 resolveParent），委托 FastImportRewriter 后 CAS update-ref 切回。行为改进：drop 根提交由旧版"静默无效"（map 回退原 hash 全 identity，提示成功实际没删）改为显式报错。
5. **WorktreeOps.ts**：仅更新 2 处注释（commit-tree → fast-import），代码零改动。README.md 目录树同步（GitExecutor/HistoryRewriter 描述 + 新增 FastImportRewriter/historyRewritePlan 条目 + DropCommitDialog 注释）。

关键设计决策：**拒绝 fast-export 增量模型**（drop 需把被删提交的增量 filemodify 并入子提交，可能引入合并冲突），保留"完整 tree"模型（每条用原 tree 顶层条目 deleteall+全量 M 重建，永不冲突、内容不变）。1000+ 条重建从 N 次 execFile 进程收敛为 2 次长驻进程（cat-file --batch + fast-import），提速 1~2 个数量级；接口签名（rewriteCommitMessage/dropCommit/onProgress）与 UI 层零改动。read_lints 全绿；lint/tsc/i18n/icons 验证移交用户。

**审查后修复 3 处（同日）**：(1) **严重回归守卫**——rewrite 非祖先目标（分析后切分支/竞态）时新版会把分支 CAS 移动到无关提交链（旧版仅静默无效），RewritePlan 新增 markedHashes 集合，rebuildDag 守卫 `markedHashes.has(headHash)` 不满足即报"该提交不在当前分支的历史上"（同时兜底空重建集）；(2) 进度回调恢复每条一次（原每 100 条导致 <100 条时 0→100 跳变），事件循环 yield 保留每 100 条；(3) sanitizeIdent 防御扩到 `<`/`>`（流式协议下尖括号破坏 "author NAME <EMAIL>" 行结构，旧 env 传参路径免疫）。用户实测确认重写"刷一下"完成属预期（旧版 1 秒/条 → 新版秒级全量）。经验：fast-import 流式方案中"CAS 校验通过"不再蕴含"目标在当前分支上"，祖先关系必须显式守卫。
