# 持久化治理与统一数据管理面板

## Context

插件的持久化已经"长成"三套体系：约 **100+ 个 `plugin.saveData` JSON 槽**（一 key 一裸文件，落在 `data/storage/petal/<plugin>/`）、**1 个 `plugin.db`（6 张表）**、以及若干**裸文件/NDJSON/localStorage**。当前问题：

1. **没有一处能看到"插件到底存了什么"**——用户只能看到 statistics 的一个 JSON 路径（且路径是伪路径），各功能清理入口散落在 5 个面板里。
2. **备份能力写好了但没接线**：`src/utils/settingsBackup.ts` 的整目录 zip 备份/还原**全仓 0 调用、0 UI**；s3Backup 的全量备份又把运行中的 `plugin.db` 直接打进 zip，无一致性保障。
3. **规则未定义**：key 命名四种风格并存（kebab / camel / 无分隔 / 带 `.json` 后缀），无注册表、无审计脚本，`AGENTS.md` 只有 SQLite 一节，缺"槽位生命周期 / 备份契约 / 迁移规则 / README 存储章节"。
4. **已确认的持久化缺陷**（不是猜测，均有行号）：
   - `feature-flags.json` **从不落盘**：`src/index.ts:136` 传入 `plugin.dataDir`（运行时 undefined）→ 永远降级 localStorage；思源每次启动端口变化导致窗口源变化，冷启动开关回落到默认值（`src/config/settings.ts:279-308` 自述）。
   - `encryption_password.json`：key 自带 `.json` 后缀，且**明文存密码**（`src/features/encryption/types/storage.ts:9,34-35`）。
   - `global-password` 双归属：pageLock 写 `{hash,salt}`，generalSettings 按 `string` 读，且 `clearAllSettings()` 会**删掉页面锁的全局密码**（`generalSettings/types/storage.ts:349,383`）。
   - `gitPush/managers/indexDir.ts:27` 把 `plugin.dataDir` 当**工作区根**再拼 `storage/petal/...`，与 `sqliteDb.ts` 的语义冲突（当前被 undefined 掩盖）。
   - 路径推导三套并存，`statistics`/`passwordVault` 给用户展示的是 `/storage/petal/...` 伪路径。
5. **写放大**：`rssReader-items`（标记一篇已读重写约 1.2MB）、`git-push-analysis-cache`（实测 1.49MB / 6786 条）、`git-push-op-logs`、`statistics-history`（每天 +1 无裁剪）等增长型集合仍整份 JSON 重写，违反 `AGENTS.md` 已有的"写放大判据"。

**本轮目标**（已与用户确认）：产出审查报告 + 定义持久化规则 + 建存储注册表与审计 + 做**一个独立功能面板**统一汇总/导出/导入/备份/还原/重置；**不实际迁移数据到 SQLite**，只产出迁移清单与判据（P0 = `rssReader-items`、gitPush 分析/报告/日志缓存）。

### 关键设计裁决

1. **注册表只承载元数据，不搬 key**。`StorageSlot` 记录 owner/kind/key/增长性/敏感性/可导出可重置；各 feature 的 `types/storage.ts` 仍是唯一写入路径。用 `audit:storage` 双向 diff（源码 key ↔ 注册表）消除漂移，**不**把 105 处 `TypedStorage` 改成从注册表 import（改动面 ≈150 文件、零功能收益）。
2. **备份一致性用 `snapshotTo()`（SQLite 在线备份 API），不是 `wal_checkpoint`**。`PluginDatabase.snapshotTo()` 已存在（`src/utils/sqliteDb.ts:407-416`）且官方支持并发写入时备份；zip 内用快照替换 `.db`、**跳过 `-wal`/`-shm`**。
3. **还原做"逻辑还原"，不覆盖活动库文件**。Windows 下运行中覆盖 `plugin.db` 会失败/损坏，且无法安全关闭各 feature 持有的连接。改为：JSON 槽按 key 写回；SQLite 表从 zip 内的临时库读出后 `DELETE + INSERT`（单表事务）；文件槽只还原 `git-push-index`。还原前**自动全量快照**。原始二进制还原（禁用插件后手动替换）只写进文档，代码留 P2。
4. **用量统计用短连接、只读**。每次盘点经 `openPluginDatabase()` 打开 → `PRAGMA query_only=ON` → `COUNT(*)`/`sqlite_master` → `finally close()`；不 checkpoint、不常驻句柄。
5. **面板形态：Dock，`position: "RightTop"`、`width: 440`**。数据管理是低频设置型控制台，Dock 可与编辑器并排；440 是为"名称 + 两行元信息 + 右侧操作"留空间，不用宽表格，避免独立窗口的 addTab/openWindow 复杂度。
6. **模块导出用单个 JSON 文件**（`{ version, exportedAt, slots: {key: value}, tables: {table: rows[]} }`），导入只接受注册表内的 slot id，未知 key 拒绝。

关键签名：

```ts
class StorageManager {
  constructor(plugin: Plugin)
  getInventory(force?: boolean): Promise<StorageInventory>
  exportModule(owners: StorageOwner[], opts?: { includeSensitive?: boolean }): Promise<Blob>
  importModule(file: File): Promise<ImportReport>
  createFullBackup(): Promise<BackupResult>
  listBackups(): Promise<BackupListItem[]>
  deleteBackup(fileName: string): Promise<void>
  restoreFromZip(file: File): Promise<ImportReport>
  resetSlot(slotId: string): Promise<SlotActionResult>
  destroy(): void
}
```

要点：
- 用量：JSON 用 `PluginStorage.load` 后 `JSON.stringify` 估算字节（不读原始文件，避免路径推导）；SQLite 用 `COUNT(*)` + `plugin.db` 文件大小；文件槽递归统计上限 5000 项（超出显示 `≥`）；缓存 TTL 30s，只按用户刷新。
- 导出：只导出 `exportable` 槽；`sensitive` 默认排除，需显式勾选。
- 导入/还原：先校验 slot id 全部在注册表内，再自动全量备份；SQLite 每表一个 `withTransaction`；完成后 `emitCustomEvent("storageRestored")` + 提示"请重载插件"，不自动 reload。
- 重置：`core` 槽与 `sensitive` 高敏槽不可重置；`git-push-index` 目录删除需二次确认。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 还原覆盖活动数据 | 强制先全量快照；SQLite 单表事务；失败即停并返回逐槽报告 + 快照路径；UI 二次确认 |
| 注册表与 feature 常量漂移 | `audit:storage` 双向 diff + `registry.spec.ts`；新槽位与注册表同 PR |
| 审计脚本误报 | 只匹配已知构造/常量形态；`scripts/audit-storage.config.json` 维护 `ignoreKeys` 并写明原因；动态 key 降级为 warning |
| 面板刷新卡顿 | 按需刷新 + 30s 缓存 + 文件槽递归上限 + 分组折叠；<200 槽位不做虚拟滚动 |
| feature-flags 修复首启回默认 | 文件缺失时保留 localStorage 回退；内核就绪后立即补写；文档说明"仅首次冷启动一次" |
| 快照临时文件被纳入备份 | 临时目录放 `data-backup/.tmp/`（扫描目录之外），`finally` 清理 |
| `indexDir` 路径改写 | 解析结果与现状同为 `<ws>/data/storage/petal/<name>/git-push-index`，启动日志打印一次便于真机核对 |

真机手动验证（不做浏览器自动验证）：
1. 完全退出思源 → 关闭某功能 → 重启 → 开关保持关闭，且 `petal/<plugin>/feature-flags.json` 存在。
2. 打开数据管理 Dock：总占用与 `petal/<plugin>`、`plugin.db`、localStorage 三键吻合；数据目录为**绝对路径**且可复制。
3. 按模块导出（如 gitPush）→ 得到 JSON → 导入 → 项目数/日志条数一致；导入前自动快照存在。
4. 全量备份 → `data-backup/sn-plugin-*.zip` 出现；用 7-Zip 确认 `plugin.db` 非空且**无 `-wal/-shm`**；还原后重启，数据一致。
5. `rssReader-items`（1MB+）、`git-push-analysis-cache`（1.5MB）在面板中显示大小/条数，刷新 <2s 且 UI 不冻结。
6. 重置 `git-push-index` 后 gitPush 可重建索引；恢复默认后 `global-password` **仍存在**，页面锁可解锁。

## 明确不做

- 不迁移任何现有槽位到 SQLite（只出清单/判据/表结构）。
- 不重命名 100+ 现有 key（只修 `encryption_password.json`），存量标 `legacyName`。
- 不做运行中整目录（含 `plugin.db` 二进制）覆盖还原；不实现"暂存目录 + marker"。
- 不合并 4 处 `DatabaseSync` 连接、不统一 `user_version`（登记为 P1 架构债）。
- 不升级加密体系（`settingsCrypto` 硬编码密钥不动），encryption 仅做 key 迁移 + 落盘加密。
- 不动 s3Backup 的 UI/调度/保留策略，只修备份一致性。
- 不做按槽位粒度导入，不做虚拟滚动/分页。
